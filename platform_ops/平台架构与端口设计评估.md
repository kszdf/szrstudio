## 三、发现的问题

1. **8500 无日志重定向**：nssm AppStdout/AppStderr 未配置（server_8500.log 0 字节），排障只能靠猜。
2. **8500 加载旧代码**：服务自 8/24 未重启，本轮对 server.py 的改动（motion 命名、MOTION_WORKERS 开关）未生效。
3. **LocalSystem 无代理**：8500 跑在 LocalSystem，读不到用户级 clash(7897) → 云端任务 TTS 偶发失败（重启bat文档已记载该问题）。
4. **双看门狗冗余且冲突**：
   - nssm 服务 HEYGEMWatchdog → `heygem_watchdog.py`（7:00-22:00 工作时段、60s 轮询、尊重 22:00 资源清理）
   - 计划任务 HEYGEMWatchdog → `heygem-watchdog.ps1`（每 5 分钟，无维护窗口概念）
   - 两者都拉起 heygem-gen-video / heygem-tts → 22:00 清理会被 ps1 抢先拉起，维护窗口形同虚设。
5. **双前端职责重叠**：8385 工作台（本地直出，只有数字人/滚动字幕）与 8080 Laravel（SaaS 队列）并行；
   **8385 没有 motion（幕后音·动态画面）入口**——新形式只能走 8500 API/CLI。
6. **heygem-tts(18180) 与 dashscope API TTS 并存**：qwen_tts 走 API，容器用途未确认，疑似旧路径冗余。
7. **死容器**：hgt-ui（3 周前退出）、heygem-tts-old（12 天前退出，watchdog 已声明排除）。
8. **死文件**：`python-pipeline/watchdog_8500.ps1` 无任何引用。
9. **端口 8383/8385 相邻易混**、8080/8500 相似，无统一文档；生产环境变量（MOTION_WORKERS 等）未落盘。

## 四、重新设计建议

### 1. 出片入口收敛
- **统一走 8500 服务**：motion/scroll/avatar 三种模式只在 8500 暴露；8385 工作台的出片按钮改为调 8500（或新增 motion 入口），消除"绕过服务、直跑引擎"的旁路。
- 好处：并发闸（3 任务）、QC 门禁、重试、版本、发布链路全部生效；本地直跑仅保留给 CLI/调试。

### 2. 服务环境规范化（nssm AppEnvironmentExtra）
```
MOTION_WORKERS=12
MOTION_TTS_WORKERS=4
HTTP_PROXY=http://127.0.0.1:7897
HTTPS_PROXY=http://127.0.0.1:7897
```
- 并行渲染 12 进程、并行 TTS 4 路；**代理注入解决 LocalSystem TTS 不稳**（`_child_env_with_proxy` 会回落到环境变量）。

### 3. 日志规范化
- 8500：AppStdout/AppStderr → `D:\heygem_data\runtime-logs\8500-server.log`（滚动 10MB）。
- 8385：已有 studio_service.log，保持。

### 4. 看门狗收敛
- **保留 nssm `heygem_watchdog.py`**（有维护窗口、有日志、轮询更勤），**停用计划任务 heygem-watchdog.ps1**（需管理员执行 `schtasks /change /tn HEYGEMWatchdog /disable`）。
- 或反向：若 ps1 更简单可信，停 nssm 服务。二选一，避免双拉。

### 5. TTS 统一
- 确认 heygem-tts(18180) 是否还有调用方；若无，停容器+删镜像（约 27GB 可回收）。

### 6. 清理
- 死容器 hgt-ui / heygem-tts-old（docker rm）；死文件 watchdog_8500.ps1。
- 死镜像（composer:latest / 旧的 swr 镜像）按需 `docker image prune`。

### 7. 重启规范
- 统一「平台一键重启」管理员 bat：写 env + 日志重定向 → 重启 8500（+可选 8385）→ 校验 /health + frp + docker。
