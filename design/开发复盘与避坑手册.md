# 开发复盘与避坑手册（szrstudio 活页）

> 文档定位：**项目开发过程中的"错题本"**。所有重复现象、经验教训在此沉淀，每次动手开发前先翻一遍，避免重犯同类错误。
> 维护规则：每踩一个新坑或总结出一条新经验，立即追加到对应分类下，**不覆盖旧条目**（保留历史便于复盘趋势）。
> 配套：本手册与 `分阶段开发实施规范.md`（开发纪律）、`后端商用化重构规划.md`（阶段目标）同为开发准绳。
> 触发纪律（用户 2026-07-30 13:13 明确）："所有开发过程中出现的重复现象、经验、教训你都要自己记住并复盘，不要重复犯同样或类似的错误。"

## 〇、使用纪律（每次开发必做）

1. **动手前**：读本节 + 相关分类，确认本次改动不会撞上已知坑。
2. **开发中/后**：凡出现以下任一情况，立刻追加条目：
   - 同一类错误第二次出现（重复现象）
   - 因假设而非实测导致返工（如凭空估性能/硬件）
   - 交付物因手滑（无效值/残留字样/语法）被打回
   - 与外部系统（Git/GitHub/ Docker/网络）交互踩坑
3. **复盘频率**：每完成一个阶段，回看本手册统计高频坑，针对性加固规范。

## 一、需求/方向类（先确认再动手）

### L1-1 方向跑偏：默认心智替代用户真实对象
- **现象**：首次按"商业短视频 App（移动端消费产品）"做高保真，用户纠正——"是 WEB 界面优化，不是抖音发布页"，真实对象是**优化现有 8385 工作台**，终端用户是内容运营而非 C 端观众。
- **教训**：涉及"做一个 XXX 界面/系统"时，先确认三件事——① 是新建还是优化现有对象？② 终端用户是谁（运营/老板/消费者）？③ 形态是 Web 还是移动端？别用自己默认的"赛道心智"替用户拍板。
- **避免**：动手前用一句话复述对象+用户+形态，等确认或明显无歧义再开工。

### L1-2 功能堆砌：做了用户明确说"别做"的能力
- **现象**：原型加"直播间"屏，用户砍掉——"有那么多成熟直播平台，就别做没竞争力的功能，能自动出片发布已 OK"。
- **教训**：用户一旦说"XX 不做了/没竞争力/交给外部平台"，即从范围剔除并记入"砍掉清单"，后续不再偷偷加回。聚焦核心价值（本平台=自动化出片+质检+发布分发）。
- **避免**：每加一个功能前自问"这是用户要的核心，还是我想当然？"，拿不准就列进待确认而非直接做。

### L1-3 误判堆功能优先级：消费级花活 vs 生产工具可用性
- **现象**：早期花大量精力做拇指热区/信息流广告/电商挂车，偏离"生产工作台"本质。
- **教训**：生产工具优先可用性与信息密度，不是消费 App 的沉浸/转化逻辑。UI 改造始终围绕"让运营更快出片"。

## 二、技术判断类（先实测再下结论）

### L2-1 性能/硬件凭假设，未实测即下结论
- **现象**：基于"本地可多开 2-4 个 HEYGEM 灶台"给出并发方案，用户要求查本机配置后，`nvidia-smi` 实测 RTX 5060 **仅 8GB 显存**，跑 1 路稳、2 路极易 OOM（呼应此前 137 崩溃），原"2-4 路"结论作废。
- **教训**：凡涉及硬件容量、并发上限、性能、显存/内存/磁盘余量、网络带宽的结论，**先跑实测命令再写方案**，不靠拍脑袋估算。
- **避免**：出方案前清单式核查——`nvidia-smi` / `wmic memorychip` / `df` / `iperf` 等，把实测值写进文档而非"估算"。

### L2-2 重复造轮子：未核查现有能力就动手
- **现象**：用户要求"把异步队列接进 8385"，实际 `rewrite_studio.py` 早已完整实现 `QUEUE`/`queue_worker`/`/api/queue`。若照做会重写一遍。改为做**只读独立监控页**补 UX 缺口（ETA+完成提醒）。
- **教训**：任何"接 XX 能力/加 XX 模块"需求，先 grep 现有代码确认是否已存在；存在则优先复用/旁路增强，不重写。
- **避免**：动手前用 Grep 检索关键字（如 queue / workspace / storage / auth），把"已有/无"写进方案起点。

### L2-3 双后端并存，老单体硬打补丁
- **现象**：线上标准库单体（2072 行）与 `szrstudio/` FastAPI 草案并存，若直接在单体上加多租户会变成意大利面。
- **教训**：统一技术栈是地基，新能力一律进新结构，不在老单体硬塞；通过端口/路由隔离并存，验证后切 NSSM 指向。
- **避免**：新增架构级能力前，确认落在哪个后端，不跨边界污染。

### L2-4 工作区副本 ≠ 真实运行文件，且可能是带 bug 的旧版
- **现象**：阶段0 要改 8385，本工作区 `szrstudio/rewrite_studio.py` 与真实运行文件 `D:/heygem_data/gpt_sovits/rewrite_studio.py` 经 `diff` 确认**不同**——工作区副本是**旧版**，标题解析还停在已修复 bug 之前（裸正则、会触发 L3-2 的失败）。改工作区副本 = 白改 + 把旧 bug 带回去。
- **教训**：NSSM 服务 HGTStudio 的 `AppParameters` 指向 `D:/heygem_data/gpt_sovits/`，**真相源永远是那里**，工作区只是归档副本。改后端前先用 `diff`/读真实文件确认，改完再把最新版同步回工作区副本纳入 git（单向同步：真→副本，绝不反向覆盖）。
- **避免**：后端改动流程固定：① `Get-ItemProperty HKLM:\...\HGTStudio\Parameters` 确认真实路径 → ② 改真实文件 → ③ `diff` 校验 → ④ 同步回工作区副本 → ⑤ 提交 git。

### L2-5 凭记忆说"有 subprocess 注入"，实测无
- **现象**：规划阶段写"修 subprocess.Popen 命令注入点"，动手 grep 实测——全文 5 处 subprocess（Popen/run）**全部 list 形式传参、零 `shell=True`**，用户可控字段（title/subtitle/model/name）都是独立 list 元素追加，经典 shell 注入实际不存在。
- **教训**：安全类整改必须**先 grep 实测**再定性，不能照搬上游规划/记忆里的"已知问题"。本例真实价值是补 `name` 路径穿越校验（但实测 `name` 在 API 路径捕获组里不参与路径拼接，穿越也不成立）——最终仅保留 list 写法、标注"已审计无 shell 注入"。
- **避免**：安全/性能/容量类结论，统一"先 grep/跑命令实证 → 再决定改不改 → 改完注释标注审计结论"。

## 三、代码质量类（交付前必校验）

### L3-1 前端手滑：无效 CSS 值 / 误插语句 / 残留字样
- **现象**：`studio_prototype.html` 浅色改造时手滑写出 `5b6party` 等无效颜色值；误插顶层 `if(a.lock)` 语句破坏脚本；品牌面板残留"商用阶段"字样。
- **教训**：任何 HTML/JS/CSS 交付物，落地前必须：
  1. 跑语法校验（node 查 JS、py_compile 查 py）；
  2. 人工 grep 关键词（如"试用/内部/即将/阶段"等禁用词）；
  3. 抽查 CSS 值合法性，不留无效 token。
- **避免**：交付清单固定三步：语法校验 → 禁用词扫描 → 视觉/值抽查。

### L3-2 解析壳脆弱导致合法输入失败
- **现象**：`/api/generate_title` 正则 `[\s\S]` 被误写为 `[\\s\\S]`，字符类退化只匹配字面 `\ s S` → 合法 JSON 也匹配不上；且隔离测试时手敲单反斜杠误判通过。
- **教训**：解析外部/模型返回时，优先 `json.loads` 直解 + 去代码围栏 + 宽松兜底；**单元测试必须用真实样例复现**，不能手敲近似输入通过就算过。
- **避免**：凡解析逻辑，写最小复现用例（真实 LLM 返回、带围栏、超长）三形态全过再算完成。

### L3-3 防御性代码手滑写出 SyntaxError（破坏式bug：文件损坏→服务跑旧码）
- **现象（2026-07-30 实测重灾）**：修复 topics_cache 双重序列化时，手滑把防御块写进函数**调用 paren 内部**——`_tc = body.get(...)` 跟在 `search_and_create(..., ` 后面，调用括号直到 8 行后才用 `)` 闭合，中间那段 `if isinstance(...)` 成了非法语法 → 整文件 `SyntaxError`。后果：**真实文件损坏**，NSSM 重启时服务**加载失败、静默回退跑旧码**，导致所谓"已修复"实际从未上线；再次真打接口复现旧崩溃 `'str' object has no attribute get'` 才暴露。
- **教训**：① 任何把"中间加工变量"塞进已有函数调用参数区的写法都极危险，正确做法是**先取变量 → 加工 → 再单独调用函数**；② **改完 Python 必须真跑 `py_compile` 对真实文件**，不能凭"应该没问题"或只编译过片段就声称"通过"；③ 服务重启后须用脚本真打一次目标接口验证修复确实生效（代码在文件≠运行进程有它）。
- **避免**：Python 改动交付三连——(a) `python -m py_compile 真实文件.py` 确认 0 错误；(b) 重启服务（8385 须管理员，普通权限 Restart-Service 无权停 SYSTEM 进程）；(c) 脚本真打目标接口断言修复生效。三者缺一不可，任一步没做就不算完成。

## 四、外部系统交互类（Git / Docker / 网络）

### L4-1 GitHub 推送连环坑
- **现象**：① 仓库无 git 身份 → 设仓库级本地身份；② 远程是 https 无 push 凭证 → 改用 SSH（`git@github.com:kszdf/szrstudio.git`）；③ `pull --rebase` 遇 5 个本地未跟踪但远程已存在文件挡路 → 临时备份 `/tmp` 解决再原样移回（无丢失）。
- **教训**：推之前先确认——远端协议（SSH 还是 https）+ 凭证是否就绪 + 是否需先 fetch/rebase。挡路文件先备份再处理，绝不清理式删除。
- **避免**：推送前固定动作：`git remote -v` 看协议 → 确认 SSH key/凭证 → `git fetch` + `git pull --rebase`（挡路文件备份后处理）→ `git push`。

### L4-4 https 远程 push 在无头环境卡死（2 分钟无响应）
- **现象**：阶段0 提交后 `git push origin main`（remote 当时是 https）在后台挂起 2 分多钟无输出——无头/无凭证缓存环境不会弹窗，直接阻塞。同仓之前 f8b662a 是用 SSH 推成功的。
- **教训**：**本仓库固定用 SSH 远程**（`git@github.com:kszdf/szrstudio.git`），不用 https。若 `git remote -v` 显示 https，先 `git remote set-url origin git@github.com:kszdf/szrstudio.git` 再推。
- **避免**：推送前先 `git remote -v`；是 https 立刻改 SSH；push 卡住就停掉换 SSH，别干等。

### L4-2 测试假象：shell curl 中文转义干扰判断
- **现象**：Git Bash `curl` 测改写/标题/试听接口，因中文转义误报空稿件/400；改用 Python 发 `json` 请求后全正常——非平台 bug。
- **教训**：测含中文的请求体接口，**用 Python（json 模块）发请求**，别用 shell curl（转义易错、难排查）。
- **避免**：接口联调统一用 Python 脚本打真实 HTTP，不靠 shell 手写 curl。

### L4-3 HEYGEM 容器不随 Docker Desktop 自动 up
- **现象**：用户说"Docker 已开"，`docker ps` 却显示 `heygem-gen-video` 为 Exited(137)；手动 `docker start` 后才响应。根因 137=OOM。
- **教训**：验证出片链路前，先 `docker ps` 确认容器 Up，不是看 Docker Desktop 开了就行；OOM 的根因对策是"一次一条排队出片"而非硬多开。
- **避免**：出片类验证步骤固定先 `docker ps | grep heygem`，未 Up 先 `docker start`。

## 五、运行态类（改了不等于生效）

### L5-1 代码改了运行进程仍是旧版
- **现象**：后端 `rewrite_studio.py` 修复标题 bug（文件层改好、py_compile 通过），但 NSSM 服务 HGTStudio（SYSTEM 进程）仍跑旧代码 → 服务端不生效。
- **教训**：8385 是 NSSM 服务，**任何后端改动必须管理员重启 HGTStudio + 浏览器强刷才生效**；普通权限重启杀不掉 SYSTEM 进程。
- **避免**：改完后端即提醒用户"待管理员重启 + 强刷"；本地测用独立端口/进程验证，不指望旧服务。

### L5-2 字段名与接口契约不一致导致假"模特不存在"
- **现象**：续测 render 接口误用 `model_id` 字段（前端发的是 `model`）→ 两次报"模特不存在"；改回 `model` 键立刻成功。
- **教训**：打接口前先读前端实际发出的字段名/键，别凭记忆或旧命名假设；字段错会伪装成业务逻辑错误。
- **避免**：联调先抓前端真实 payload（或读前端源码发字段），再构造测试请求。
