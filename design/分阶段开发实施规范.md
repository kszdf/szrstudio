# 分阶段开发实施规范（szrstudio 落地版）

> 文档定位：把"先核心、后扩展、验证可行再推进"的开发纪律，落到本项目的可执行动作上。
> 配合阅读：`后端商用化重构规划.md`（阶段目标）、`后端多租户存储设计草案.md`（存储契约）。
> 适用对象：接手 szrstudio 的工程师；老板据此验收"是否按阶段、是否留了扩展口"。
> 铁律前提：原 `rewrite_studio.py` / `rewrite_studio.html`（8385 生产环境）**始终保持零改动**，新代码一律进 `szrstudio/` 新后端。

---

## 〇、核心纪律（违反即打回）

1. **架构先确认，再写业务代码**：每阶段动手前，本阶段的三件套（规划 / 依赖 / 接口）必须先冻结并通过评审。
2. **接口一次到位**：跨阶段交互点必须定义为稳定抽象（接口 / 协议 / 配置项），后续阶段只补实现、不破契约。
3. **契约不冲突**：阶段 N 的产出不得让阶段 N+1 必须推翻重做；新代码与现 8385 单体**并存不打架**（通过端口 / 路由 / 目录隔离）。
4. **复用优先，禁止重复造轮子**：动手前先核查现有代码（尤其 8385 已实现的异步队列）与工具，能复用绝不重写。
5. **依赖显式化**：模块前后置依赖、阶段边界、职责必须写清楚，确保分步时各模块可独立推进且最终无缝衔接。

---

## 一、阶段规划（与商用重构规划对齐）

### 阶段 0 — 安全地基（零现金，内部必做）
**目标**：在不动生产的前提下，堵住对外开放前的硬伤，并铺"抽象接口"地基。
**边界**：只加不改核心生产链路；所有新增代码在 `szrstudio/security/` 与 `szrstudio/storage/` 下独立模块。
- Token 鉴权中间件（局域网防误触/泄露）
- 修 `subprocess.Popen` 命令注入点（审计现有 8385 调用，抽成安全封装）
- HEYGEM 自愈看门狗（已交付 `design/scripts/heygem_watchdog.py`）
- **`Storage` 抽象接口落地（本地实现）** —— 这是阶段三平滑上云的命根子，现在零成本必须做

### 阶段 1 — 内部闭环试用（MVP）
**目标**：稳定生产、收集反馈，无对外入口。
**边界**：沿用 8385 单体生产，新后端只承接"队列可视化 / 监控"旁路能力。
- 队列前端化（排队位 + ETA + 完成通知，复用 `design/scripts/queue_monitor.py` 思路回流主界面）
- 本地存储按 `ws_` 目录隔离规范试点（即便单租户，先跑通路径规则）

### 阶段 2 — 对外内测（统一技术栈 + 多租户）
**目标**：营销官网 + 邀请制注册 + 控制并发成本。
**边界**：核心能力从 8385 单体**迁到 FastAPI**，灭双后端；结构 = 路由层 / 服务层 / 队列层 / 存储层。
- JWT 鉴权 + 用户/角色（admin / 内部 / 租户）
- `workspace_id` 多租户隔离（所有资源带 ws_id，查询必带——见存储草案红线）
- 用量计费引擎（先记账不收费）
- 独立营销落地页（不走生产工作台）

### 阶段 3 — 正式商用租赁
**目标**：计费上线 + 弹性渲染 + 开放 API。
- 对象存储 + CDN（Storage 接口切 `oss` 实现，业务零改）
- 套餐 / 支付 / 按量计费
- Webhook 通知（签名校验）
- 云 GPU 弹性 Worker（队列积压时按需起）
- 营销落地页 + API 开放

## 二、依赖关系图（谁等谁，谁不依赖谁）

```
[阶段0: Storage抽象] ──┐
[阶段0: 安全封装]   ──┤
[阶段0: 看门狗]     ──┴─► [阶段1: 队列可视化] ──► [阶段2: FastAPI迁移]
                                                        │
                                                        ├─► [阶段2: JWT鉴权]
                                                        ├─► [阶段2: 多租户隔离] ──► 依赖[阶段0: Storage抽象]
                                                        └─► [阶段2: 计费引擎(记账)]
                                                                  │
                                                                  ▼
                                                        [阶段3: 对象存储/CDN] ──► 依赖[阶段0: Storage抽象]
                                                        [阶段3: 支付计费]      ──► 依赖[阶段2: 计费引擎]
                                                        [阶段3: 云GPU Worker]  ──► 依赖[阶段1: 队列模型]
                                                        [阶段3: Webhook]       ──► 依赖[阶段2: JWT/多租户]
```

**关键依赖说明**
- **阶段 0 的 `Storage` 抽象是全局地基**：阶段 2 多租户、阶段 3 上云都依赖它。若阶段 0 不抽接口，阶段 3 必返工 → 这正是"架构一次到位"要防的。
- **阶段 1 不阻塞阶段 0**：队列可视化是旁路，可与安全地基并行。
- **阶段 2 是分水岭**：只有完成 FastAPI 统一，阶段 3 的弹性/计费才有挂载点；阶段 3 各项之间相对独立，可并行。
- **8385 生产链路**：贯穿阶段 0~1 仍是主力，阶段 2 被新后端取代，阶段 3 完全退役（迁移脚本见存储草案第九章）。

## 三、接口预留清单（现在就定义，后续只实现）

> 原则：每个跨阶段边界，先冻结"调用长什么样"，实现可以后补。标注【阶段X定义·阶段Y实现】。

### 3.1 Storage 抽象（【阶段0定义·阶段0本地实现·阶段3 OSS实现】）
```python
# szrstudio/storage/abc.py
class Storage(ABC):
    @abstractmethod
    def save(self, ws_id: str, rel_path: str, data: bytes) -> str: ...
    @abstractmethod
    def get_url(self, ws_id: str, rel_path: str, expire_sec: int = 3600) -> str: ...
    @abstractmethod
    def delete(self, ws_id: str, rel_path: str) -> None: ...
    @abstractmethod
    def list(self, ws_id: str, prefix: str) -> list[str]: ...
```
- 切换仅改配置 `STORAGE_BACKEND=local|oss`，业务代码零改。
- **扩展口**：新增云厂商只需加一个实现类，不动调用方。

### 3.2 任务队列服务（【阶段1定义·阶段1本地串行·阶段3云GPU】）
```python
# szrstudio/queue/service.py
class QueueService:
    def submit(self, ws_id: str, job_spec: dict) -> job_id: ...
    def status(self, job_id: str) -> dict: ...   # queued/rendering/done/failed + ETA
    def cancel(self, job_id: str) -> bool: ...
    # 扩展口：Worker 池策略（本地1 / 云GPU N）通过配置注入，接口不变
```
- 复用 8385 现有 `QUEUE` + `queue_worker` 串行模型，抽成独立服务。
- **扩展口**：`CloudGPUWorker` 后期实现同接口，队列积压时自动扩容，调用方无感。

### 3.3 鉴权上下文（【阶段0定义中间件·阶段2接JWT】）
```python
# szrstudio/security/context.py
# 请求入口解析出 workspace_id / user_id / role，注入 request 上下文
# 所有 Repository 方法强制要求 ws_id（或不传即从上下文取），漏写即抛异常
```
- 阶段 0 先用单层 Token 占位，阶段 2 换 JWT，业务侧取 ws_id 的方式不变。
- **扩展口**：角色权限矩阵（admin/内部/租户）通过配置表定义，新增角色不改代码。

### 3.4 计费引擎（【阶段2定义·阶段2记账·阶段3收费】）
```python
# szrstudio/billing/engine.py
class BillingEngine:
    def quote(self, spec: dict) -> cost: ...        # 纯函数：时长/分辨率/双人对播/克隆音 → 额度
    def pre_deduct(self, ws_id: str, cost) -> txn_id: ...   # 幂等预扣
    def refund(self, txn_id) -> None: ...                  # 失败回退

```
- 阶段 2 只记账展示（前端"生成额度条"），阶段 3 接支付不改引擎契约。

### 3.5 Webhook 出口（【阶段2定义接口·阶段3实现】）

### 3.6 渲染器适配（【阶段0定义接口·阶段3接云】）

## 四、各阶段边界与职责（独立推进、无缝衔接）

| 阶段 | 输入 | 输出 | 职责边界 | 不做什么 |
|---|---|---|---|---|
| 0 | 现有 8385 代码、本机环境 | 安全封装 + Storage接口 + 看门狗 | 堵安全洞、抽地基 | 不碰生产链路、不做多租户 |
| 1 | 阶段0地基 | 队列可视化 + 本地隔离试点 | 内部稳定生产、收集反馈 | 不对外开放、不引数据库 |
| 2 | 阶段0/1产物 | FastAPI后端 + JWT + 多租户 + 记账 | 统一技术栈、可邀请注册 | 不接支付、不起云GPU |
| 3 | 阶段2后端 | 存储上云 + 计费 + 弹性 + API | 正式商用 | 不回头改阶段0~2契约 |

**衔接保证**：相邻阶段通过第三节的接口对接；阶段 N 的输出物（抽象/协议）就是阶段 N+1 的输入契约，因此"分步时各模块可独立推进且无缝衔接"。

## 六、风险红线（与现有规划一致，此处强调"阶段纪律"维度）

1. **未抽 `Storage` 接口就上云** → 业务代码大面积返工（阶段0必须完成）。
2. **阶段2在 8385 单体上硬打多租户补丁** → 双后端越改越乱，必须走 FastAPI 统一。
3. **查询/文件操作漏 `workspace_id`** → 串户事故，中间件强制注入 + 评审打回。
4. **命令注入点未修就上云** → 云上暴露面更大，阶段0必须修。
5. **无鉴权对外开放** → 商业机密泄露 + 算力被白嫖，阶段2前不得对外。
